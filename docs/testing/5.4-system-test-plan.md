# 5.4 System Test Plan (functional and non-functional)

**Project:** InternLink Uganda · **WBS:** 5.4 System testing · **Owner:** Aryatusinguza Arthur
**Status:** Plan complete; executed 30 Oct 2026 where the system parts exist

## 1. Purpose and approach

System testing checks the finished system against every functional requirement (SR01–SR20) and non-functional requirement (NFR01–NFR10) in WBS Section B. Each test case uses the acceptance condition from the WBS.

Evidence comes from three places:

- **DB:** `06_tests.sql` (PR #2) for database rules
- **API:** `tests/` (pytest) for the matching API
- **Manual:** browser and device checks once the UI exists

A requirement passes only when it has been verified through the **real application**. Database-level evidence alone is marked "Partly verified".

**Status key:**

| Status | Meaning |
|---|---|
| ✅ Pass | Verified |
| 🟡 Partly verified | Rules verified in the database, not yet through the app |
| ❌ Fail | Defect found |
| ⛔ Blocked | The feature isn't built or pushed yet |

## 2. Entry and exit criteria

- **Entry:**
  - Unit tests (5.2) pass
  - Integration tests (5.3) run
  - A build is deployed to a test environment with seed data loaded
- **Exit:**
  - Every **Must** requirement passes, or has an approved change request
  - No open High-severity defects
  - NFR01 load test passes
  - Results are recorded in Section 5

**NFR01 test conditions:**

- One 4-core Windows laptop ran PostgreSQL, the API (uvicorn, one process, 8 database connections) **and** the load generator. The generator used CPU the system would otherwise have had.
- Before the run, measured outside the API:
  - one request alone takes about 50–100 ms
  - the database serves at most about 17–28 recommendations per second, whatever the pool size
- 200 students with a 10 s pause need about 20 per second, so requests queue up.
