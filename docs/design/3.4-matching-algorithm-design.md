## 1. Purpose

The matching engine gives each student a ranked list of the internship listings that fit them best, so they don't have to search by hand (UR-S3). This document defines what data it reads, how it scores a student against a listing (0–100), how it filters and ranks, and how the API returns the result.

## 2. Where the logic lives

| Part | Where | Owner |
|---|---|---|
| Eligibility filters, scoring, ranking | `fn_recommendations(student_id, limit, min_score, weights…)` in PostgreSQL | Lubega (code), Arthur (design) |
| Recommendation service: listing details, matched/missing skills, profile check, time limit | `matching_engine/service.py` (Python) | Arthur |
| HTTP endpoint | Web framework, not chosen yet (3.1) | Arthur (4.6.2) |

Keeping the rules in one place means the score a student sees, the score stored in `applications.match_score`, and the score in tests are always the same.

## 3. Input data (PR #2 schema)

| Data | Table / column |
|---|---|
| Student programme and family | `student_profiles.programme_id` → `programmes.programme_group` |
| Student skills / interests | `student_skills`, `student_interests` (shared lists, not free text) |
| Student location | `student_profiles.preferred_location`, `willing_to_relocate` |
| Listing programmes | `listing_programmes` (none = open to all) |
| Listing required skills | `listing_skills` where `is_required = true` (optional skills don't count) |
| Listing tags / sector | `listing_interests`, `listings.sector` |
| Listing location | `listings.location`, `listings.is_remote` |

Skill spellings are unified by the `skill_synonyms` table when profiles and listings are saved.

## 4. Eligibility filters

A listing can only be recommended if **all** of these are true (same rules as view `v_open_listings`):

1. `status = 'open'`
2. The company is **verified** (SR07)
3. `application_deadline` is today or later
4. `slots_filled < slots`

Listings the student has **already applied to are kept** and returned with `applied = true`, so the UI can label them instead of hiding them.

## 5. Scoring

Four parts, each between 0 and 1:

```
score = round( 100 × (wP·P + wS·S + wI·I + wL·L) / (wP + wS + wI + wL) )
```

| Part | Weight | Value |
|---|---|---|
| **P** Programme relevance | 0.35 | 1.0 same programme · 0.5 same `programme_group` · 0.0 otherwise · 0.5 if the listing is open to all programmes |
| **S** Skills | 0.40 | required skills the student has ÷ required skills · 0.5 if the listing lists none |
| **I** Interests | 0.15 | see 5.1 |
| **L** Location | 0.10 | 1.0 remote or same location · 0.5 elsewhere but willing to relocate · 0.0 otherwise |

- If the student has **no preferred location**, L is left out and the other weights are rescaled (the divisor drops `wL`).
- The weights are function parameters with these defaults. Any change goes through the change-request procedure (WBS E.2), since unclear weights are a listed scope-creep risk (E.3).
- Rounding happens once, at the end, in exact `NUMERIC` arithmetic (half away from zero, i.e. half-up for positive scores). The function is `STABLE` and uses no randomness, so the same data always gives the same score (SR20).

### 5.1 Interest part I and SR20

**Current definition:** I = (student interests that match the listing's sector or tags) ÷ (number of the **student's** interests).

**Known defect:** dividing by the student's interest count means adding any interest that doesn't match **lowers** every score, which breaks SR20 ("more overlap ⇒ score never lower"). On the seed data there are **141** such cases. For example, adding "Agriculture" to student 1 drops the Software Developer Intern from 79 to 77.

**Proposed fix (sent to Lubega for review):** I = (listing topics the student has) ÷ (number of the **listing's** topics), where the listing's topics are its tags plus the interest named like its sector. A listing with no topics gets 0.5, like P and S. Tested on a copy of the seed database: **0** SR20 violations. 161 of 165 database tests still pass, and the other 4 only need their expected example scores updated (e.g. 79 → 87).

## 6. Ranking

1. Drop listings with a score below `min_score` (default **20**). The list may be shorter than 10.
2. Sort by score (high first), then S (high first), then `posted_at` (newest first), then `listing_id` (lowest first, always unique).
3. Return the first `limit` rows (default **10**, SR03), numbered from rank 1.

### 6.1 Worked example (seed student 1, Nakato: BSc SE, Python/SQL/Flask, interests Software and Data, prefers Kampala, not willing to relocate)

| | Software Developer Intern | Data Analyst Intern | Accounting Intern |
|---|---|---|---|
| P | 1.0 (same programme) | 0.5 (computing group) | 0.0 |
| S | 2/3 (Python, SQL of Python, SQL, React) | 1/3 (SQL of SQL, Excel, Statistics) | 0 |
| I | 1/2 (Software of her 2 interests) | 1/2 (Data) | 0 |
| L | 1.0 (Kampala) | 0.0 (Mbarara) | 1.0 |
| Total | .35 + .267 + .075 + .10 = .792 | .175 + .133 + .075 + 0 = .383 | .10 |
| **Score** | **79** | **38** | **10** (below 20, dropped) |

These match Lubega's database tests M01–M04.

## 7. Recommendation service and API (4.6.2)

`matching_engine.service.recommend_for_student(conn, student_id, k=10)` calls `fn_recommendations` and adds, per result: title, company, deadline, the four-part breakdown, `applied`, and `matched_skills` / `missing_skills` (required skills only) for the "why recommended" UI (4.3.3).

```
GET /api/v1/students/me/recommendations?limit=10
Authorization: Bearer <JWT>      (role must be student, SR17 / NFR05)
```

```json
{
  "algorithm": "fn_recommendations v1",
  "count": 1,
  "results": [{
    "rank": 1, "listing_id": 1, "title": "Software Developer Intern", "company": "TechCo Ltd",
    "score": 79, "breakdown": {"programme": 1.0, "skills": 0.667, "interests": 0.5, "location": 1.0},
    "applied": true, "matched_skills": ["Python", "SQL"], "missing_skills": ["React"],
    "deadline": "2026-11-29"
  }]
}
```

| Code | When | What the UI does |
|---|---|---|
| 401 / 403 | Not logged in, or not a student | Redirect / access denied (logged, SR17) |
| 422 `PROFILE_INCOMPLETE` | No profile, or no skills (`ProfileIncomplete`) | Prompt to complete the profile |
| 503 `MATCHING_UNAVAILABLE` | Database error or longer than 4 s (`MatchingUnavailable`) | "Couldn't load recommendations" + **Retry** (NFR07) |

A student only gets their own recommendations (`me`); no other student ID can be passed in (NFR06).

## 8. Performance (4.6.3)

Target: 95% of requests under 5 s with **200 concurrent** students (NFR01), with 10,000 students and 2,000 open listings (NFR09).

- Filters use index `ix_listings_open`; the whole calculation runs inside the database.
- The service sets `statement_timeout` to 4 s per request and returns 503 instead of hanging.
- `07_load_test.sql` times 50 students **one at a time**. Still to do: a concurrent load test (k6 or Locust, 200 virtual students for 5 minutes, report p95) once the endpoint exists.
