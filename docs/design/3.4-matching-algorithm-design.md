## 1. Purpose

The matching engine gives each student a ranked list of the internship opportunities that fit them best, so they don't have to search by hand (UR-S3). This document defines:

- what data the engine reads,
- how it scores one student against one opportunity (0–100),
- how it filters and ranks opportunities into a top-10 list,
- how it meets the speed and reliability targets,
- the API the Student module will call.

## 2. Requirements the design must meet

| ID | What it needs | How this design meets it |
|---|---|---|
| SR20 | Score is a number from 0 to 100 | Weighted sum of three parts, each between 0 and 1, times 100 and rounded (Section 5) |
| SR20 | Score is reproducible | Pure function: no randomness, no clock, fixed rounding (Section 5.5) |
| SR20 | More overlap never gives a lower score | Each part measures how much of the opportunity the student covers, so extra matches can only raise it (Section 5.6) |
| SR03 | Top-10 list, highest score first, in under 5 s | Filter, score, sort, take 10 (Section 6) |
| NFR01 | Under 5 s for 95% of requests at 200 concurrent students | Database-side filtering, in-memory scoring, caching, load test (Section 8) |
| NFR07 | A failed calculation must not crash the page | Clear error response plus a retry option in the UI (Section 9) |
| NFR08 | Engine is a separate, unit-testable module | Scoring is a standalone module with no database or web code (Section 10) |

## 3. Input data

The engine needs the following fields. **Lubega's ERD (3.2) has the final names**. This list shows what the engine has to read.

| Field | Type | Example |

| `skills` | list of skill IDs (from a skills table) | python, sql, react, git |
| `interests` | list of sector/topic IDs | fintech, data science |

### 3.2 Opportunity

| Field | Type | Example |
|---|---|---|
| `sector` | sector ID | fintech |
| `target_programs` | list of program IDs (empty = open to all) | BSc CS, BSc SE |

### 3.3 Request to the database design (3.2)

Skills, interests and programs should be **picked from shared lists, not typed as free text**. If one student types "JS" and a company types "JavaScript", the engine can't tell they're the same skill. Shared lists fix this at the source.

If free text has to stay, the engine will clean values before comparing them. It will lowercase them, trim spaces, and map known synonyms (e.g. `js` → `javascript`, `ml` → `machine learning`) using a small synonym table.

### 3.4 Mapping to the database schema (PR #2, PostgreSQL 16)

The database design (PR #2) uses shared lists, as requested in 3.3. The engine reads it through `matching_engine/db.py`:

| Engine field | Database source |
|---|---|
| `student.program` | `student_profiles.programme_id` (matched by **id**, because programme names repeat across universities) |
| `student.skills` / `interests` | `student_skills` → `skills.name`, `student_interests` → `interests.name` |
| Program family | `programmes.programme_group` (e.g. `computing`, `business`) |
| `opp.target_programs` | `listing_programmes.programme_id` (none = open to all) |
| `opp.required_skills` | `listing_skills` where `is_required = true` |
| `opp.tags` | `listing_interests` → `interests.name` |
| `opp.sector` | `listings.sector`, compared with the student's interest names |
| Hard filters (4.1) | view `v_open_listings` (open, verified company, deadline ≥ today, slots left) plus "not already applied" |
| Tie-breakers | `listings.application_deadline`, `listings.posted_at`, `listings.listing_id` |

The database only supplies data and the hard filters. **All scoring and ranking happen in the Python engine**, so there is one copy of the rules (NFR08). The SQL function `fn_recommendations` in PR #2 uses different rules (Section 11, item 6).

## 4. Pipeline overview

```
 Student requests recommendations
            │
            ▼
 1. Load student profile ──► profile incomplete? ──► return "complete your profile"
            │
            ▼
 2. Fetch candidate opportunities (hard filters, done in the database)
            │
            ▼
 3. Score each candidate (0–100)
            │
            ▼
 4. Drop scores below MIN_SCORE
            │
            ▼
 5. Sort (score desc, then tie-breakers)  ──►  take top K (default 10)
            │
            ▼
 6. Return list + score breakdown + matched/missing skills
```

### 4.1 Hard filters (step 2)

An opportunity can only be recommended if **all** of these are true:

1. `status = Open`
2. The company is **Verified** (SR07: unverified companies can't have live listings)
3. `deadline` is today or later
4. `slots_remaining > 0`
5. The student has **not already applied** to it

These are yes/no rules, so they run in the database query. They don't affect the score.

## 5. Scoring

The score combines three parts, matching WBS 4.6.1:

```
score = round( 100 × ( W_SKILL × S_skill  +  W_PROG × S_prog  +  W_INT × S_int ) )
```

Each part `S_*` is between 0 and 1.

### 5.1 Weights (draft, needs team sign-off)

| Part | Weight | Reason |
|---|---|---|
| Skills overlap `W_SKILL` | **0.45** | Skills best predict whether the student can do the work |
| Program relevance `W_PROG` | **0.35** | Universities approve placements against academic requirements (UR-U2), so program fit matters a lot |
| Interest match `W_INT` | **0.20** | Matters for motivation, but weaker than ability or eligibility |

The weights are kept in one config file, not hard-coded, and must add up to 1.0. Any later change to the weights goes through the change-request procedure (Section E.2 of the WBS), because unclear weights are listed as a likely source of scope creep (E.3).

### 5.2 Skills overlap `S_skill`

The share of the opportunity's required skills that the student has:

```
S_skill = |student.skills ∩ opp.required_skills| / |opp.required_skills|
```

- If the opportunity lists no required skills, `S_skill = 0.5` (neutral: there's no evidence either way).

**Why this formula and not Jaccard similarity?** Jaccard divides by *all* skills on both sides, so a student who adds an unrelated skill (e.g. "photoshop") would score *lower* on a data-analyst post. That would break SR20 ("more overlap ⇒ score never lower") and would punish students for filling in their profiles. Coverage of required skills has neither problem.

### 5.3 Program relevance `S_prog`

| Case | `S_prog` |
|---|---|
| Student's program is in `target_programs` | 1.0 |
| Student's program is in the same **program family** as one of the targets (e.g. Computing: SE, CS, IT, IS) | 0.6 |
| `target_programs` is empty (open to all) | 0.5 |
| None of the above | 0.0 |

Program families are a small lookup table (program → family) stored with the seed data (4.2.2).

### 5.4 Interest match `S_int`

```
sector_hit = 1 if opp.sector is in student.interests, else 0
tag_cover  = |student.interests ∩ opp.tags| / |opp.tags|

if opp.tags is empty:   S_int = sector_hit
else:                   S_int = 0.6 × sector_hit + 0.4 × tag_cover
```

### 5.5 Reproducibility rules

- Scoring is a **pure function** of (student profile, opportunity). It doesn't read the clock, the database or any random value. Time is only used in the hard filters.
- Rounding is **round-half-up to a whole number**, done once at the end, never in between.
- To avoid floating-point drift (e.g. 32.4999… instead of 32.5), the sum is computed in fixed precision (decimal, or ×10,000 integers) before rounding.
- Each response includes `algorithm_version` (e.g. `"v1"`), so any score can be traced to the weights that produced it.

### 5.6 Why "more overlap ⇒ score never lower" holds

- `S_skill`, `S_int`'s `tag_cover` and `sector_hit` all have the **opportunity's** list size as the bottom of the fraction. Adding a matching item to the student's profile raises the top of the fraction. Adding a non-matching item changes nothing.
- `S_prog` doesn't depend on skills or interests.
- All weights are positive, so if any part goes up, the total can't go down.

This is checked by a property test in Section 10.

### 5.7 Pseudocode

```
function score(student, opp, cfg):
    S = set(normalize(student.skills))
    R = set(normalize(opp.required_skills))
    s_skill = (|S ∩ R| / |R|) if |R| > 0 else 0.5

    if student.program in opp.target_programs:              s_prog = 1.0
    else if family(student.program) in families(opp.target_programs): s_prog = 0.6
    else if opp.target_programs is empty:                   s_prog = 0.5
    else:                                                   s_prog = 0.0

    I = set(normalize(student.interests))
    T = set(normalize(opp.tags))
    sector_hit = 1 if opp.sector in I else 0
    if |T| == 0: s_int = sector_hit
    else:        s_int = 0.6 * sector_hit + 0.4 * (|I ∩ T| / |T|)

    total = cfg.W_SKILL * s_skill + cfg.W_PROG * s_prog + cfg.W_INT * s_int
    return {
        score:     round_half_up(100 * total),      # fixed precision
        breakdown: { skills: s_skill, program: s_prog, interests: s_int },
        matched_skills: sorted(S ∩ R),
        missing_skills: sorted(R − S)
    }


function recommend(student_id, k = 10):
    student = load_profile(student_id)
    if student.program is missing or student.skills is empty:
        return error PROFILE_INCOMPLETE

    candidates = fetch_open_verified_unapplied(student_id, today)   # hard filters in DB
    results = [ score(student, opp, cfg) + opp for opp in candidates ]
    results = [ r for r in results if r.score >= cfg.MIN_SCORE ]

    sort results by:
        1. score            descending
        2. deadline         ascending   (closing soon first)
        3. posted_at        descending  (newer first)
        4. opportunity_id   ascending   (final, always unique)

    return first min(k, cfg.MAX_K) of results, with algorithm_version
```

### 5.8 Configuration

| Setting | Default | Meaning |
|---|---|---|
| `W_SKILL`, `W_PROG`, `W_INT` | 0.45 / 0.35 / 0.20 | Weights, must add up to 1.0 |
| `MIN_SCORE` | 20 | Leave out weak matches; the list may have fewer than 10 |
| `DEFAULT_K` / `MAX_K` | 10 / 50 | Results returned by default / at most |
| `CACHE_TTL` | 10 min | How long a student's list is cached (Section 8) |
| `TIMEOUT` | 4 s | Stop and return an error before the 5 s limit |

## 6. Worked example

**Student:** BSc Software Engineering. Skills: python, sql, react, git. Interests: fintech, data science.

| | A: Junior Data Analyst | B: Network Support Intern | C: Frontend Developer Intern |
|---|---|---|---|
| Sector | fintech | telecom | software |
| Target programs | BSc CS, BSc SE, BSc Statistics | BSc IT | BSc SE, BSc CS |
| Required skills | python, sql, excel | networking, linux, git | react, javascript, css |
| Tags | data science, banking | infrastructure | web development |
| `S_skill` | 2/3 = 0.667 | 1/3 = 0.333 | 1/3 = 0.333 |
| `S_prog` | 1.0 (exact) | 0.6 (same Computing family) | 1.0 (exact) |
| `S_int` | 0.6×1 + 0.4×½ = 0.8 | 0 | 0 |
| Total | 0.30 + 0.35 + 0.16 = 0.81 | 0.15 + 0.21 + 0 = 0.36 | 0.15 + 0.35 + 0 = 0.50 |
| **Score** | **81** | **36** | **50** |
| Rank | 1 | 3 | 2 |

For A, the response says the student matched **python, sql** and is missing **excel**. The Recommendations UI (4.3.3) can show this as "why this was recommended".

## 8. Performance plan (feeds 4.6.3)

Target: **95% of requests under 5 s with 200 concurrent students** (NFR01), planning for up to **2,000 open listings** (NFR09).

1. **Filter in the database.** Index `status`, `deadline` and `company_id` so step 2 is one fast query.
2. **Prepare listings when they're saved.** Clean and store each listing's skill/tag lists when it's created or edited, not on every request.
3. **Score in memory using sets.** Each check is roughly constant time. 2,000 listings × a few comparisons each takes well under 100 ms.
4. **Cache per student** for `CACHE_TTL`. Clear the cache when the student edits their profile or applies, or when listings change.
5. **Time limit:** stop at `TIMEOUT` (4 s) and return 503 instead of hanging.
6. **Load test** in 5.4 using a free tool (k6 or Locust): 200 virtual students for 5 minutes against seeded data, reporting p95 response time. Pass = p95 < 5 s.

## 9. Failure handling (NFR07)

- Any error inside scoring is caught at the API boundary and returned as `503 MATCHING_UNAVAILABLE` with a short message. Internal details never go back to the user.
- One bad listing (e.g. corrupt data) is skipped and logged, so it doesn't fail the whole list.
- The Recommendations UI always shows a **Retry** button on error. The rest of the student dashboard keeps working.

## 10. Testing plan (feeds 5.2–5.4)

**Unit tests (5.2)**

| Test | Check |
|---|---|
| Bounds | Every score is a whole number from 0 to 100 |
| Determinism | Same input 1,000 times → same output every time |
| Monotonicity (property test) | Adding a skill or interest to a student never lowers any opportunity's score |
| Worked example | Section 6 gives exactly 81, 50, 36 |
| Empty required skills | `S_skill = 0.5` |
| Open-to-all listing | `S_prog = 0.5` |
| Tie-breaking | Equal scores sort by deadline, then posted date, then ID |
| Weight config | Weights that don't add up to 1.0 are rejected at startup |

**Integration tests (5.3):** recommendations leave out closed, expired, full, unverified and already-applied listings. Applying to a listing removes it from the next list.

**System tests (5.4):** SR03 (top 10, sorted, under 5 s), SR20, NFR01 load test, NFR07 retry behaviour.
